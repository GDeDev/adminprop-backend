## Notas de operación

- Las dos migraciones nuevas usan `CREATE INDEX` común porque `job_executions`, `owners` y `renters` son chicas. El índice único parcial de `job_executions` no se puede declarar en `schema.prisma`; lo cubre `src/shared/prisma/lookup-indexes.spec.ts`.
- `prisma migrate deploy` en producción: la primera migración agrega una columna nullable (sin reescritura) y el índice; las filas viejas quedan con `slot` NULL y no participan del único.

### Cómo desplegar las migraciones nuevas

1. **Antes** de migrar contra una base con datos: `npm run db:check-duplicates`. Si lista algo, limpiar esas filas (es lo mismo que haría fallar la migración de únicos, que aborta sin cambiar nada).
2. `prisma migrate deploy`. Las tres migraciones `CONCURRENTLY` van solas; si una falla queda un índice `INVALID` (`DROP INDEX CONCURRENTLY IF EXISTS <nombre>` antes de reintentar).
3. Después de migrar: `SELECT conrelid::regclass, conname FROM pg_constraint WHERE contype = 'c' AND NOT convalidated;`. Lo que aparezca violaba una fila vieja: corregirla y `ALTER TABLE ... VALIDATE CONSTRAINT`.

Verificado: `prisma migrate deploy` sobre una base vacía propia y `prisma migrate diff` (migraciones contra `schema.prisma`) sin deriva.
